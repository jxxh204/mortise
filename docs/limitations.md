# v0.2의 지원 범위와 제약

Mortise v0.2는 React의 계약 기반 UI 연결에 HTTP Query·Action 실행을 추가한 프로토타입이다. 이전 설계 대화에서 논의한 원격 RSC 배포까지 구현한 버전은 아니다.

## 서버 실행과 보안 경계

- RSC, Flight 스트림 생성·조합, SSR, hydration을 제공하지 않는다. `ui/server`를 사용하는 입력은 지원하는 것처럼 처리하지 않고 오류로 보고해야 한다.
- HTTP 모드에서 Query·Action 구현은 서버에서 실행한다. 로컬 `attachDomain` 방식도 있으므로 파일 이름만으로 원격 실행을 보장하지 않는다.
- UI wrapper는 UI 연결을 담당한다. 서버 경계는 HTTP 전송 설정과 서버 핸들러에서 구현한다.
- 예제 데이터는 서버 프로세스 메모리에 저장된다. 브라우저 새로고침과 서버 재시작은 다르다. 서버 재시작이나 개발 중 서버 모듈 재로딩 시 데이터가 초기화될 수 있으며 DB 영속성은 없다.
- 예제의 `cart-main`, `cart-other` 같은 입력은 데이터 선택용 식별자다. 로그인 세션이나 사용자 인증을 구현한 것은 아니다. 실제 서비스의 사용자 소유권 격리를 증명하는 예제로 사용하지 않는다.
- 서버의 `authorize` 콜백은 필수지만, 구현 내용은 애플리케이션의 책임이다. 항상 허용하는 콜백은 인증이나 소유권 검사가 아니다. 항목이 조회 결과에 존재한다는 사실도 사용자의 수정 권한을 뜻하지 않는다.
- `domain.ts`와 계약은 HTTP 모드에서도 클라이언트에 전달될 수 있다. 비밀 정보와 서버 구현은 이 선언들에서 import하지 않는다.
- 플러그인은 HTTP 클라이언트 빌드에서 도메인 내부의 `queries`, `actions`, `model`, `server`, `.server.*` 및 서버 진입점 import를 막는다. 프로젝트의 다른 위치에 임의의 이름으로 둔 비밀 파일까지 자동 판별하는 보안 분석기는 아니다.
- Query의 전체 반환값이 JSON 응답에 포함된다. UI 계약의 projection은 비밀 필드를 제거하는 보안 필터가 아니다. Query는 공개 가능한 조회 모델만 반환해야 한다.

### 요청 경계

서버 핸들러는 POST JSON 요청을 받으며, 기본 요청 크기 제한은 64 KiB다. Origin이 있는 요청은 설정한 허용 origin과 비교한다. Node 어댑터의 `publicOrigin`은 외부에서 접근하는 서버 주소로 고정해 제공해야 한다.

Origin이 없는 CLI·서버 요청은 허용할 수 있다. Origin 검사는 인증을 대신하지 않으며 CORS 허용 헤더를 추가해 임의의 다른 사이트를 자동 지원하는 서버도 아니다. 실제 로그인, CSRF 정책, 세션·토큰 검증은 애플리케이션 배포 환경에 맞게 구성해야 한다.

의도적으로 공개한 `MortiseHttpError`의 상태·코드·메시지만 클라이언트에 전달하고, 예상하지 못한 오류는 일반 오류로 변환한다. 공개 오류 메시지에 비밀 정보를 넣지 않는다.

## 계약이 보장하는 것

계약은 상태와 명령의 구조를 표현한다. 서로 다른 도메인이 같은 계약에 명시적으로 참여해야 하며, 같은 이름을 갖는 임의의 데이터를 전역 검색해 연결하는 규칙은 아니다.

타입과 스키마가 맞아도 업무 의미까지 증명되지는 않는다. 예를 들어 `setQuantity(3)`를 어떤 도메인은 절대 수량 3으로, 다른 도메인은 기존 수량에 3을 더하는 것으로 구현하면 계약의 의미가 깨진다. 이런 의미는 계약 문서와 도메인 테스트로 검증해야 한다.

타입을 `any`로 우회하거나 검증되지 않은 외부 데이터를 반환하면 TypeScript만으로 안전성을 보장할 수 없다. 빌드 시 연결 검사와 실제 실행 시 데이터 검증의 범위를 혼동하지 않는다.

HTTP 응답은 JSON으로 표현 가능한 값으로 제한한다. `Date`, `Map`, `Set`, `BigInt`, 클래스 인스턴스, 순환 참조를 그대로 전송하지 않는다. 데이터가 필요하면 문자열이나 일반 객체로 명시적으로 변환한다. 반환값 전체가 `undefined`인 void 명령은 지원한다.

현재 원격 프록시는 같은 scope에서 여러 계약의 명령을 같은 Action 이름으로 연결하면 모호성 오류를 낼 수 있다. 서로 다른 명령의 Action target을 구분한다.

## 범위와 UI 재사용

폴더는 연결할 도메인을 선택한다. 실제 데이터의 도메인 인스턴스와 반복 항목은 런타임 범위에서 선택한다. 같은 폴더에 속한다고 모든 UI가 하나의 전역 상태를 공유하지 않는다.

항목 계약을 사용하는 UI는 해당 `Each` 범위 안에 배치해야 한다. 파일 이동만으로 어느 상품이나 예약을 다룰지 추론할 수는 없다. UI를 다른 도메인으로 이동했을 때 계약이 없거나 필드·명령이 맞지 않으면 연결을 수정해야 한다.

계약에 드러내지 않은 내부 모델과 외부 API를 UI가 직접 참조하면 이동 가능한 UI라는 전제를 깨뜨린다. 이 버전의 연결 기능을 완전한 프로젝트 전체 의존성 정책 엔진으로 간주하지 않는다.

## 렌더링과 갱신

내부 조회·변경 관리는 TanStack Query 5를 사용한다. Mortise는 그 위에서 도메인·항목 범위와 계약 연결을 제공한다. React 렌더러 자체를 대체하지 않는다.

조회 결과 갱신과 컴포넌트 remount는 같은 의미가 아니다. React key, 컴포넌트 타입, 배치가 유지되는 경우 로컬 상태를 유지할 수 있지만, 사용자가 key나 트리 구조를 바꾸면 React의 일반적인 상태 초기화 규칙을 따른다.

selector가 바뀌지 않은 값을 선택하더라도 부모 렌더, props 변경, 로컬 상태 변경 등 다른 React 경로의 렌더까지 없어진다고 보장하지 않는다. 렌더 횟수보다 필요한 화면 상태가 일관되게 표시되는지가 우선이다.

현재 `useCapability(contract)`는 계약 상태 전체를 구독한다. 계약별 selector overload는 아직 없다. 루트 상태의 일부를 선택하려면 `useDomain(selector)`를 사용할 수 있다. Proxy 기반 속성 접근 추적은 구현하지 않는다.

`domain`과 `services`의 참조 또는 입력이 바뀌면 실행 인스턴스가 바뀔 수 있다. `services={{ ... }}`처럼 렌더마다 새 객체를 생성하기보다 모듈 상수나 `useMemo`로 안정적인 참조를 제공한다.

명령은 도메인 인스턴스 안에서 순서대로 실행한다. 다른 인스턴스나 외부 서버의 변경까지 직렬화하지는 않는다. 낙관적 UI와 서버 간 충돌 해결은 이 기능에 포함되지 않는다.

### 명령 결과와 변경 이후 실패

`execute`는 오류를 `command.error`로 제공하며 다음 결과를 반환한다.

| status | 의미 |
| --- | --- |
| `success` | Action 결과와 갱신을 정상 처리함 |
| `validation-error` | 실행 전 입력 또는 인스턴스 상태 검증 실패 |
| `action-error` | Action 실행의 성공 응답을 확인하지 못함 |
| `result-error` | Action이 반환한 결과가 출력 계약을 위반함 |
| `refresh-error` | Action 반환 이후 조회 갱신에 실패함 |

변경 요청 후 네트워크가 끊기면 서버에서 이미 저장했는지 알 수 없을 수 있다. `committed: 'unknown'`은 이 결과 불명 상태를 나타낸다. `committed: true`는 Action이 반환한 뒤 결과 검사나 재조회에서 실패했을 때도 가능하다. 두 경우 모두 변경 명령을 무조건 재시도하면 안 된다.

`committed`는 전송 계층이 관찰한 실행 단계이며 데이터베이스 트랜잭션의 증명이 아니다. Action이 일부 변경을 한 뒤 예외를 던지면 결과를 단정할 수 없다. 중복 요청 방지, 트랜잭션, 저장소 버전 비교, 충돌 해결은 애플리케이션에서 별도로 설계해야 한다.

## UI 변환과 타입 검사

UI 주입 변환은 `export default function`의 단일 매개변수에 붙인 `UI<typeof Contract, Props>` 표식을 대상으로 한다. 모든 React 컴포넌트 문법을 해석하는 범용 변환기는 아니다. async, generic, 화살표 함수, re-export 형태는 지원하지 않는다.

계약은 런타임 값이므로 `import type`으로만 가져올 수 없다. UI 함수에 주입되는 타입과 외부 JSX에서 요구할 타입이 다르므로 생성된 `mortise:ui/...` 공개 import와 선언 파일을 사용해야 한다. 소스 파일을 직접 import하면 TypeScript가 주입 매개변수까지 외부 props로 요구할 수 있다.

계약 상태와 명령 입력·출력은 타입 추론을 제공하지만, 현재 `ProviderOptions`의 문자열 alias와 `ExecutionContext`의 root·scope 값·services는 전체 데이터 모델을 정적으로 검사하지 않는다. 잘못된 별칭이나 외부 데이터는 실행 시에도 검사해야 한다.

## 아직 제공하지 않는 배포 기능

- 도메인별 서버 배포와 배포 레지스트리
- 원격 RSC와 Client 에셋 manifest의 버전 연결
- 여러 서버에 걸친 배포 라우팅과 인증 시스템의 자동 구성
- 여러 탭·사용자·서버 사이의 실시간 상태 동기화
- 영속 저장, 분산 트랜잭션, 서버 전체에서의 명령 실행 순서 보장

이 기능들이 필요해지면 현재 계약·범위 모델을 유지하면서 별도의 서버 런타임과 전송 프로토콜을 설계해야 한다.
